# 对象快照、不可变设计与无状态工具方法

## 1. 快照保存的是“当时的事实”

业务系统常同时存在两类数据：

- 当前数据：产品现价、客户现地址、用户当前部门；
- 历史事实：成交单价、下单地址、审批时的内容。

历史记录如果只引用当前对象，当前对象变化时历史也会变化。报价转订单、购物车结算、合同签署和审计记录都需要在关键时刻保存快照：

```text
来源对象继续变化
        ↓ 不影响
历史快照保持转换时的值
```

快照的关键不变量是：创建成功后，其业务结果不再受来源对象后续修改影响。

## 2. Java 集合和字段保存的可能只是同一对象引用

引用可以理解为对象的地址。两个变量或两个集合即使彼此不同，也可能指向同一个可变对象：

```text
报价列表 ─┐
          ├─→ 同一个可变明细
订单列表 ─┘
```

此时修改明细会同时影响报价和订单，这叫引用别名。创建一个新列表并不自动创建新元素；判断是否真正隔离，必须沿着对象关系继续检查所有可变引用。

## 3. 浅拷贝只复制外层，快照需要切断可变引用

浅拷贝通常只创建新的外层容器，元素仍是原对象。深层隔离则为目标模型创建新的元素，并复制转换时需要的值：

```text
报价列表 → com.xxby.Quotation.QuotationItem
订单列表 → 新的 com.xxby.Order.OrderItem
```

并非所有引用都必须无限复制。`String`、`BigDecimal`、`LocalDate` 等对象本身不可变，共享它们不会让外部篡改其内容；`ArrayList`、数组和带 Setter 的业务对象则需要复制或受控封装。

正确问题不是“有没有使用 copy 方法”，而是：

> 外部是否还持有一条能够改变快照可观察状态的路径？

## 4. 不可变对象需要同时保护字段、元素和集合结构

不可变对象创建完成后，其可观察业务状态不能再改变。常见设计是：

- 构造时完成必要校验和赋值；
- 字段保持私有，固定字段优先使用 `final`；
- 不提供改变状态的 Setter；
- 不接收或返回未经保护的可变对象；
- 集合元素也具有不可变语义。

`final` 对引用字段只表示不能重新指向另一个对象，不代表所指对象不能变化：

```text
final List<Item>：不能换掉这份 List 引用
List 内部元素：仍可能被增删或修改
```

同样，`List.copyOf()`主要阻止调用者增删外层列表，是浅层保护。如果元素可变，调用者仍可能通过元素方法破坏状态。因此需要区分：

1. 字段引用是否固定；
2. 集合结构是否可修改；
3. 集合元素是否可修改；
4. 是否还共享来源对象中的可变元素。

## 5. 静态工厂方法可以表达对象的创建语义

构造器只能使用类名，静态工厂可以用方法名说明对象如何产生：

```text
new com.xxby.Order.OrderDraft(...)          只表达创建对象
com.xxby.Order.OrderDraft.from(quotation)   表达从报价转换
```

静态工厂方法仍必须返回一个合法对象，并承担入口校验。它适合表达：

- `from(...)`：从另一种对象转换；
- `of(...)`：由一组值创建；
- `parse(...)`：从文本解析；
- `copyOf(...)`：复制并建立隔离。

命名不能替代正确性。无论构造器还是工厂方法，都要保证创建成功后的不变量，并拒绝不允许的来源状态。

## 6. 工具类应共享行为，不应意外共享一次计算的状态

工具类通常具有：

- 私有构造器，避免创建无意义实例；
- 静态方法，直接通过类名调用；
- 不保存与某次调用相关的可变静态字段。

`static` 方法和 `static` 可变状态不是一回事：

```text
static 方法：多个调用者复用同一段行为
static 计数器：多个调用者共享同一份结果状态
```

如果统计结果属于一次方法调用，就应使用局部变量。局部变量每次调用都会重新建立，不会把上一次结果带入下一次调用，也更容易进行并发使用和独立测试。

只有真正属于整个类、生命周期和并发规则都明确的数据，才适合静态共享。为了少传一个参数或少写一个局部变量而引入静态状态，通常会制造调用顺序依赖。

## 7. 线性扫描的核心是循环不变量

对无序数组进行完整计数时，需要检查全部 `n` 个元素，时间复杂度为 `Θ(n)`；只使用固定数量的局部变量，额外空间复杂度为 `O(1)`。

计数过程的关键不变量是：

> 当前计数值，等于已经检查部分中目标值出现的次数。

开始时尚未检查元素，计数为零；每扩大一次已检查范围，都要继续保持该事实；处理完整个数组后，它自然成为全数组的正确结果。

复杂度描述增长趋势，不是精确的机器指令数：

- `O(n)`：工作量上界与输入长度同阶；
- `Ω(n)`：问题至少需要同阶工作量；
- `Θ(n)`：上下界同阶。

完整统计不能在第一次匹配时提前结束；“是否存在”与“出现多少次”具有不同的停止条件。

## 8. 测试必须验证隔离和调用生命周期

快照测试不能只检查刚转换完成时的值相同，还要主动修改来源对象，再验证目标对象保持原值。这个测试能排除“复制了列表但共享了元素”的错误实现。

无状态工具方法至少应连续调用两次，并使用不同输入验证第二次结果不包含第一次残留。单次调用正确无法排除静态累加器污染。

还要区分两类测试证据：

- 一次性验收：证明当前版本在一组数据上通过；
- 仓库自动测试：以后每次构建都能阻止回归。

如果源码不在 Maven 配置的源码目录内，`mvn test` 的绿色结果并不能证明它已被编译和测试。构建成功只覆盖构建工具实际发现的文件。

## 9. 可迁移的常见失败模式

### 9.1 目标对象直接保存来源对象

这只是建立引用关系，不是建立历史快照。来源变化会污染历史结果。

### 9.2 只复制列表，不复制可变元素

外层容器独立，但元素引用仍共享，属于浅拷贝。

### 9.3 把一次调用的计数器声明为静态字段

第一次调用可能正确，后续调用会累加旧结果，并在并发调用时产生竞争。

### 9.4 只看到总构建成功，没有确认源码是否进入构建范围

独立练习目录、命名不符合测试发现规则或未配置的模块可能完全没有被执行。

## 10. 可迁移审查清单

- 当前数据变化后，历史记录是否仍保持原值？
- 新容器中的元素是新对象，还是来源对象的引用？
- 所有可变引用是否已经复制或封装？
- `final` 保护的是引用还是整个对象状态？
- 返回的集合和其中元素能否被外部修改？
- 对象创建成功后是否始终满足业务不变量？
- 静态工厂名称是否准确表达创建来源？
- 工具类是否只共享行为，没有共享一次调用的结果？
- 连续调用测试能否排除状态残留？
- 构建日志是否明确显示目标源码和测试被发现？
- 测试期望是否独立于生产计算？

## 11. 独立迁移问题

将一个可修改的购物车转换为结算快照。转换后修改购物车商品数量、当前单价或列表结构，结算快照中的商品、成交价和总额都必须保持不变。

解释并验证：哪些对象必须新建，哪些不可变值可以安全共享，为什么只复制列表不够，以及如何用一次来源修改测试排除浅拷贝实现。
