# 哈希索引、唯一键与产品目录设计

## 1. 本主题解决什么问题

业务系统经常需要完成两类操作：

- 根据唯一标识快速找到对象，例如“商品编码 → 商品”；
- 判断一批数据中是否出现重复值。

如果每次都从头遍历列表，数据量为 `n` 时，最坏需要检查 `n` 个元素。哈希集合和哈希映射通过哈希值缩小查找范围，平均情况下可以用接近固定的时间完成查询。

选择集合前，应先说清业务语义：

- `HashSet<E>` 表达“哪些值已经出现过”；
- `HashMap<K, V>` 表达“一个唯一键对应哪个值”；
- `List<E>` 表达“按顺序保存一组元素”，它不会自动提供唯一键约束。

## 2. `HashSet`：用集合成员关系进行判重

`Set.add(value)` 不只是写入操作，它还会返回本次是否真的加入了新元素：

```java
Set<String> seen = new HashSet<>();
boolean first = seen.add("A");   // true
boolean second = seen.add("A"); // false
```

因此，判重过程可以维护这个不变量：

> 集合中恰好保存已经检查过的所有不同值。

发现 `add()` 返回 `false`，说明当前值早已出现。对长度为 `n` 的输入，平均时间复杂度为 `O(n)`，最坏需要额外保存 `n` 个不同值，所以空间复杂度为 `O(n)`。

这里的“平均 `O(1)` 查找”不是永远只执行一步。哈希冲突、扩容和对象的 `hashCode()`/`equals()` 实现都会影响实际成本；极端情况下单次操作可能退化。

## 3. `HashMap`：建立唯一键到对象的索引

`Map<K, V>` 保存键值关系。产品目录可以表达为：

```text
产品编码（Key） → 产品对象（Value）
```

这里的关键不是“用了 HashMap”，而是选定了产品编码作为目录中的唯一身份。只要这个契约成立，就可以通过编码直接查询，而不必遍历全部产品。

需要特别注意 `put(key, value)` 的默认语义：键已经存在时，它会替换旧值，不会自动报错。因此，如果业务规则是“新增商品时禁止重复编码”，必须在修改映射前检查键是否存在，并在冲突时保持原目录不变。

```text
校验对象完整性 → 生成规范键 → 检查重复 → 最后写入 Map
```

这体现失败原子性：新增失败后，已有商品、目录数量和原键值关系都不能改变。

## 4. 哈希查找为什么既依赖 `hashCode()` 又依赖 `equals()`

哈希容器通常先根据键的 `hashCode()` 定位候选区域，再使用 `equals()` 确认是否真的是同一个键。

必须遵守的对象契约是：

> 两个对象如果 `equals()` 相等，它们的 `hashCode()` 必须相等。

反过来不成立：哈希值相等的两个对象仍可能不相等，这叫哈希冲突。容器必须继续比较，不能只看哈希值就认定相等。

`String`、`Integer` 等 JDK 类型已经正确实现这套契约。自定义类型若要作为键，就必须根据稳定的身份字段设计 `equals()` 和 `hashCode()`，并测试相等、不同和冲突相关行为。

## 5. 哈希键必须稳定，并且在所有入口使用同一规范

如果业务把下面三个输入视为同一商品编码：

```text
"sau32x150"
" SAU32X150 "
"Sau32X150"
```

那么新增、查询、包含判断和删除都必须先执行相同的规范化，例如去除首尾空白并按稳定语言环境转为大写。否则写入使用一种形式、查询使用另一种形式，会出现“数据明明存在却查不到”或重复数据漏检。

规范化后的编码是目录键时，不应允许对象在入库后绕过目录直接修改编码。否则会形成：

```text
Map 中的键仍是旧编码 → Value 内部已经变成新编码
```

此时索引和对象事实互相矛盾。可靠方案通常是让身份键不可变；确需改键时，由目录执行受控的“删除旧映射并建立新映射”，同时完成冲突检查。

## 6. 一份业务仓库与多个 `HashMap` 不是同一个问题

`HashMap` 只是内存中的数据结构，不自动代表数据库，也不决定系统存在几份商品仓库。

如果每个业务对象都各自创建并维护一份商品映射，确实会产生多个互不一致的目录。但正确的职责通常是：

```text
一个应用级产品目录/仓储对象
        ↓
内部使用一份 Map 建立编码索引
        ↓
需要查询产品的业务对象调用这个目录
```

进入 Spring Boot 后，可以由容器管理一个仓储组件；进入 MySQL 后，数据库表成为持久化事实来源，仓储负责查询数据库。此时 `Map` 可能只存在于测试替身、临时内存实现或有明确一致性规则的缓存中。

因此应区分：

- **数据结构**：如何在内存中组织和查找数据；
- **仓储职责**：谁拥有并管理一组业务对象；
- **数据源**：数据最终保存在哪里、哪一份是权威事实。

## 7. 枚举不仅能限制取值，还能携带展示信息

枚举适合品牌、计量单位、有限状态等取值范围明确的数据。枚举常量还能通过构造器携带附加信息：

```java
enum Level {
    HIGH("高"), LOW("低");

    private final String label;

    Level(String label) {
        this.label = label;
    }

    public String getLabel() {
        return label;
    }
}
```

`HIGH` 是稳定的程序值，`"高"` 是展示值。不要依赖 `toString()` 或枚举常量名称直接承担所有界面文案和数据库含义；程序身份、持久化值和用户展示可以有不同契约。

如果业务取值会由用户随时新增、停用或配置，通常应使用数据库实体，而不是每次修改枚举并重新发布程序。

## 8. 测试和边界验证

### 哈希判重

- `null` 输入的契约明确；
- 空数组、单元素数组没有重复；
- 相邻重复和相隔很远的重复都能发现；
- 负数、零、整数边界不被特殊处理错；
- 全部唯一时不能误报；
- 方法不应意外修改输入数组；
- 连续多次调用不能残留上一次的状态。

### 产品目录

- 首次新增后数量、查询和包含判断一致；
- 不同大小写和首尾空格仍定位到同一规范键；
- 重复新增被拒绝，失败后数量和原对象不变；
- `null`、空白编码和信息不完整对象有明确失败契约；
- 查询未知但格式合法的编码时，返回值契约明确；
- 两个目录实例是否隔离，应符合设计好的生命周期；
- 外部不能直接取得内部 `Map` 并绕过业务方法修改它。

## 9. 与相近方案的取舍

| 方案 | 平均时间 | 额外空间 | 适用情况 |
|---|---:|---:|---|
| 双重遍历判重 | `O(n²)` | `O(1)` | 数据极小、只做一次简单检查 |
| 排序后检查相邻项 | `O(n log n)` | 取决于排序方式 | 允许改变顺序，或还需要有序结果 |
| `HashSet` 判重 | `O(n)` | `O(n)` | 只需判断重复，接受额外内存 |
| `HashMap` 按编码查询 | 平均单次 `O(1)` | `O(n)` | 存在稳定唯一键，需要频繁查找对象 |

复杂度是增长趋势，不是脱离业务的唯一选择标准。数据规模、顺序要求、内存限制、键是否稳定和持久化需求都应参与决策。

## 10. 可迁移审查清单

- 我需要的是有序集合、唯一成员集合，还是键值索引？
- 业务上的唯一键是什么，是否真的稳定？
- 所有写入和查询入口是否使用同一规范化规则？
- `put()` 覆盖旧值是业务需要，还是会掩盖重复？
- 校验和冲突检查是否全部发生在修改状态之前？
- 自定义键的 `equals()` 与 `hashCode()` 是否满足契约？
- 键入库后是否还能被绕过仓储修改？
- 谁拥有这份集合，它是实例状态还是意外的全局状态？
- 当前 Map 是权威数据源、测试替身还是缓存？
- 测试是否覆盖失败后的状态不变和连续调用隔离？

## 11. 独立迁移问题

设计一个内存用户目录，使用不可重复的邮箱规范值作为键。要求支持新增、按邮箱查询和判断是否存在；邮箱忽略首尾空白和字母大小写。重复新增必须失败且不能覆盖原用户，合法但未知的邮箱按约定返回未找到。

完成后解释：为什么使用 `Map` 而不是 `List`，邮箱何时完成规范化，为什么不能让用户对象入库后自行修改作为索引的邮箱，以及未来迁移到 MySQL 时哪些规则应由数据库唯一约束再次保护。
