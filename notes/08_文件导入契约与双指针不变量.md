# 文件导入契约与双指针不变量

## 1. 外部输入必须先经过边界，再进入领域对象

文件中的文本不可信。即使文件能打开，也不代表表头、列数、字段和值域正确。可靠导入应按层次处理：

```text
打开资源
→ 验证文件与表头
→ 验证每行结构
→ 把文本转换为强类型值
→ 用领域对象验证业务规则
→ 检查跨行冲突
→ 最后写入结果集合
```

每一层解决的问题不同：列数属于结构错误，无法转换成枚举属于格式或取值错误，空商品编码属于领域错误，重复编码属于跨记录冲突。不要用一个宽泛的异常捕获把所有失败都改叫同一种错误，否则调用者虽然知道“失败了”，却不知道哪里需要修正。

## 2. 字符编码和 BOM 是输入契约的一部分

字符编码规定字节如何还原成字符。读写双方编码不一致时，中文和特殊符号就可能乱码。因此读取文本时应显式指定 UTF-8，而不是依赖操作系统默认编码：

```java
try (BufferedReader reader = Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
    // 使用 reader
}
```

某些 UTF-8 文件开头可能带 BOM。Java 读取后，BOM 可能表现为第一个字段最前面的字符 `\uFEFF`，导致肉眼相同的 `productCode` 比较失败。处理时应只在允许出现的位置识别或移除 BOM，不能对所有字段随意删除字符。

需要区分：

- UTF-8 是字符编码；
- BOM 是可能出现在文件开头的标记；
- “使用 UTF-8”不保证输入一定带 BOM，也不保证一定不带；
- BOM 测试应构造真实的 `\uFEFF`，不能只写普通空格代替。

## 3. `try-with-resources` 负责资源生命周期

文件读取会占用操作系统资源。无论正常返回还是中途抛异常，都必须关闭读取器。实现了 `AutoCloseable` 的资源可以放进 `try (...)`：

```java
try (BufferedReader reader = obtainReader()) {
    // 正常结束和异常结束都会自动 close
}
```

这比在多个 `return`、`catch` 和 `finally` 分支中手动关闭更不容易遗漏。它只负责资源释放，不会自动决定异常应该吞掉、包装还是继续向上传播。

文件不存在、权限不足和读取失败通常属于 I/O 失败，应保留 `IOException` 边界。业务格式错误则可以使用明确的参数或领域异常。打印异常后返回空对象会把“没有数据”和“读取失败”混为一谈，调用者无法可靠处理。

## 4. 字符串拆分要明确末尾空字段语义

Java 的 `String.split()` 接收正则表达式。默认调用会丢弃末尾空字符串：

```java
"A,B,".split(",").length      // 2
"A,B,".split(",", -1).length  // 3
```

导入固定列数据时，末尾空字段通常表示“这一列存在但值缺失”，不能悄悄消失，因此可使用负数 `limit` 保留它。随后仍要分别验证“列数正确”和“字段值合法”，列数为五不代表五个字段都有有效内容。

用 `split(",", -1)` 只适合当前这种受限的逗号分隔格式。真正的 CSV 还可能包含引号、字段内逗号、换行和转义；出现这些需求时应先重新定义格式契约，再考虑成熟 CSV 库，而不是不断给 `split` 打补丁。

## 5. 枚举转换建立了文本到有限取值的边界

`Enum.valueOf(Type.class, text)` 要求文本与枚举常量名称准确匹配；大小写、空白和展示中文都不会自动转换。调用前必须明确：

- 是否允许首尾空白；
- 是否区分大小写；
- 文件保存的是程序常量名、稳定代码还是中文展示值；
- 未知值应报告哪一行、哪一列。

枚举常量名适合小型受控输入，但它会让文件格式与 Java 源码名称耦合。以后进入数据库或公开 API 时，更稳定的做法通常是为业务值定义独立代码，并显式完成“外部代码 → 枚举”的转换。

异常包装应保持原因准确。只把枚举转换放入“枚举错误”的捕获范围；如果连领域对象构造也放进去，那么商品编码校验抛出的 `IllegalArgumentException` 也会被误报为枚举错误。需要包装时应保留原异常作为 cause，方便诊断。

## 6. 一次加载应拥有独立结果和清晰失败语义

如果加载器的职责是“读取一个文件并生成一份目录”，每次调用就应创建新的结果对象。不要把上一次调用的可变集合藏在静态字段或加载器字段中，否则会出现：

- 第二次加载夹带第一次的数据；
- 重复判断依赖调用顺序；
- 测试彼此污染；
- 并发调用互相影响。

还要明确失败原子性。理想契约是：加载成功时返回完整结果；任意一行失败时抛异常，不向调用者暴露半成品。局部构建一份新目录，全部完成后再返回，是实现这一契约的简单方式。

## 7. 文件测试应控制环境，而不是依赖开发机

测试不要依赖固定的个人路径和手工准备的文件。JUnit 的临时目录可以为每个测试创建独立输入，测试结束后自动清理：

```java
void importsFile(@TempDir Path directory) throws IOException {
    Path file = directory.resolve("input.csv");
    Files.writeString(file, "example", StandardCharsets.UTF_8);
}
```

高价值测试矩阵包括：

- 正常文件与仅有合法表头；
- 空文件和不存在文件；
- BOM 表头；
- 表头字段错误；
- 少列、多列和末尾空字段；
- 未知枚举值与非法领域字段；
- 文件内重复唯一键；
- 连续加载两次，结果对象与数据生命周期互相独立。

只断言异常类型可能掩盖错误分支；当多个规则使用同一种异常时，还应检查稳定的错误分类、行号或错误码。

## 8. 相向双指针依赖“有序”和单调性

相向双指针使用一个左指针和一个右指针，从有序数组两端逐步缩小搜索范围。它比双重循环快，不是因为“用了两个变量”，而是因为每次比较都能根据单调性安全排除一整批不可能答案。

在升序数组中寻找两数之和：

- 当前和太小，固定右端时，左端及其更小元素都不可能成功，因此左指针右移；
- 当前和太大，固定左端时，右端及其更大元素都不可能成功，因此右指针左移；
- 指针移动后，已排除区域不再需要检查。

关键不变量是：

> 如果答案仍然存在，那么答案一定还在当前左右指针围成的未排除区间内。

每次循环至少移动一个指针，区间最多缩小 `n` 次，因此时间复杂度是 `O(n)`，只使用固定数量变量，额外空间复杂度是 `O(1)`。双重循环需要检查大量数对，时间复杂度为 `O(n²)`。

## 9. 乘积双指针必须额外证明适用范围

加法在升序数组上具有直接单调性，但乘法遇到负数后会改变关系。例如两个负数相乘可能变成很大的正数，简单地根据当前乘积移动左右指针不再一定能安全排除答案。

因此，一个只为非负升序数组设计的乘积双指针必须把前置条件写清楚并验证：

```text
输入已升序，并且所有元素都不小于零
```

前置条件不是注释装饰。如果方法依靠它保证正确，就要由调用者明确保证，或由方法检查后拒绝非法输入。对于已确认升序的数组，只需检查最小元素就能知道是否存在负数；如果不信任“已排序”这个契约，就必须完整扫描或先验证排序。

边界条件还包括：`null`、长度不足二、零、重复元素、目标不存在，以及同一元素不能被重复使用。

## 10. 扩大类型必须发生在运算之前

两个 `int` 相加或相乘时，Java 会先按 `int` 运算，结果溢出后再赋给 `long` 也无法恢复：

```java
long wrong = left * right;        // 先发生 int 乘法
long safe = (long) left * right;  // 先提升，再发生 long 乘法
```

同样原则适用于加法。要防止中间结果溢出，至少一个操作数必须在运算前转换为更宽的类型。`long` 也有上限；选择类型时仍需结合输入范围证明不会再次溢出。

## 11. 用简单正确的实现校验优化算法

优化算法的随机测试可以使用一个容易确认正确、但速度较慢的实现作为测试预言机：

```text
随机生成小规模输入
→ 暴力检查所有数对
→ 运行双指针
→ 比较两个结果
```

暴力算法适合作为小数据正确性基准，双指针负责大数据效率。测试期望必须独立于被测实现；如果测试和生产代码使用同一套移动逻辑，两者可能一起犯错。

随机对照不能替代固定边界测试。应同时保留最小数组、无答案、重复值、整数边界、负数契约和溢出反例。一次性测试只证明当前版本接受过检查；只有纳入构建系统的自动测试才能长期阻止回归。

## 12. `TreeSet` 去重与其他集合的区别

`TreeSet` 同时提供唯一性和自然排序，所以字符去重后会重新排序。它不会保留首次出现顺序：

```text
输入 cbacba
TreeSet 结果 abc
```

- `HashSet`：去重，平均操作 `O(1)`，不保证迭代顺序；
- `LinkedHashSet`：去重并保留插入顺序；
- `TreeSet`：去重并排序，单次操作 `O(log k)`。

长度为 `n`、不同元素数为 `k` 时，使用 `TreeSet` 的总体时间约为 `O(n log k)`，额外空间为 `O(k)`。集合选择必须由输出顺序契约决定，而不是仅凭类名中有没有“Hash”。

## 13. 可迁移审查清单

- 是否显式指定文本编码，并考虑文件开头的 BOM？
- 资源是否在成功、返回和异常路径上都能关闭？
- I/O 失败与内容不合法是否具有不同契约？
- 固定列拆分是否保留末尾空字段？
- 当前格式是否已经超过简单 `split` 能可靠处理的范围？
- 结构校验、类型转换、领域校验和跨记录冲突是否分层？
- 异常信息是否准确指向行、字段和真实原因？
- 每次加载是否创建独立结果，失败时是否不会暴露半成品？
- 优化算法依赖的排序、值域和单调性是否明确？
- 类型转换是否发生在可能溢出的运算之前？
- 是否用独立暴力实现和固定边界共同检查优化算法？
- 去重后到底要求无序、保留首次顺序，还是排序？

## 14. 独立迁移问题

实现一个“客户文件导入”功能：文件使用 UTF-8，每行包含客户编码、名称和等级；客户编码在单个文件内不可重复，等级只能取有限值。要求不存在文件保留 I/O 异常，格式错误能报告行号，任意一行失败时不返回半份客户目录，并为 BOM、末尾空等级、重复编码和连续两次加载设计测试。

随后回答：如果文件允许名称中出现逗号，为什么当前拆分方案不再可靠；如果要在升序客户消费额数组中寻找两笔金额之和，双指针的哪个不变量允许排除搜索区间。
