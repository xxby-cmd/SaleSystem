# 测试隔离与状态一致性

## 1. 测试必须自包含

每个测试都应独立准备前置数据，不能依赖其他测试先执行。

```text
Arrange：准备本测试需要的状态
Act：只执行一个目标行为
Assert：验证结果和关键副作用
```

如果一个测试单独运行失败、整组运行却通过，通常说明它借用了其他测试留下的状态。

可靠测试必须满足：

- 单独运行通过；
- 整组运行通过；
- 改变执行顺序仍通过；
- 重复运行结果稳定。

## 2. `static` 可变状态会跨测试存活

`static` 字段属于类，不属于某个测试对象。在同一JVM和类加载器中，所有测试共享它。

```java
private static final List<Item> items = new ArrayList<>();
```

测试方法结束不会自动清空静态集合。前一个测试写入的数据可能让后一个测试意外触发重复校验。

临时内存实现可以在每个测试前重置：

```java
@BeforeEach
void setUp() {
    // 恢复到本测试需要的初始状态
}
```

正式设计应优先避免全局可变仓储，让每个测试创建独立的仓储实例。`@BeforeEach` 是测试隔离手段，不是对全局状态设计的长期辩护。

## 3. 默认顺序通过仍不足以证明隔离

测试框架不保证使用源码书写顺序。只验证一次完整运行，可能隐藏顺序依赖。

检查共享状态时至少做三种运行：

```text
单个测试
完整测试类
随机顺序测试
```

随机顺序失败通常不是“测试框架不稳定”，而是测试之间存在隐式依赖。

## 4. 集合保存的是对象引用

把对象加入集合后，集合保存的是该对象的引用。

```java
items.add(item);
item.changeCode("NEW");
```

如果集合中的元素和 `item` 指向同一个对象，修改 `item` 的字段后，集合中看到的也是新值。通常不需要：

- 再次把同一个对象加入集合；
- 先用 `indexOf()` 找到自己，再通过集合修改自己。

重复加入同一个对象会制造重复引用，使遍历、计数和校验产生意外结果。

使用 `indexOf()` 时还要知道：它通过 `equals()` 判断相等；未重写 `equals()` 时，默认通常比较对象身份。

## 5. 一个状态只保留一个明确修改入口

如果 Setter、`edit` 方法和集合更新互相调用，容易出现：

- 重复校验；
- 方法循环调用；
- 同一对象重复注册；
- 字段已经修改，后续步骤却失败。

可靠的修改流程是：

```text
校验输入
→ 标准化
→ 检查业务冲突
→ 一次性修改状态
```

修改失败后，原状态必须保持不变。对应测试不能只断言“抛了异常”，还应断言旧值没有被破坏。

## 6. 同一字段的所有写入路径必须遵守同一契约

构造器、Setter、编辑方法如果都能写入同一字段，就必须使用相同规则：

- 相同的空值策略；
- 相同的标准化方式；
- 相同的重复校验语义；
- 相同的异常契约。

只测试构造器不能证明Setter正确。每一种公开写入路径都需要至少一个正常测试和一个关键失败测试。

## 7. 构建依赖必须可复现

构建文件只声明实际使用的测试框架，并使用明确版本。避免 `LATEST`、`RELEASE` 等动态版本，否则同一份源码可能在不同时间解析到不同依赖。

```text
依赖最少化 + 版本明确 + IDE外构建通过
```

这是本地测试能够迁移到团队环境和CI的基础。

## 8. 代码审查清单

- 每个测试是否自行准备前置状态？
- 是否存在跨测试共享的静态可变数据？
- 单测、整组和随机顺序是否都通过？
- 修改已有对象时是否重复加入集合？
- 是否存在多个互相调用的修改入口？
- 失败后旧状态是否保持不变？
- 构造器和Setter是否执行相同标准化规则？
- 构建依赖是否最少、明确且可复现？
