# 状态建模、时间边界与可靠测试

## 1. 有限状态优先使用 `enum`

当一个对象只能处于少数几种明确状态时，使用枚举比字符串更可靠：

```java
public enum com.xxby.Quotation.QuotationStatus {
    DRAFT,
    CONFIRMED
}
```

字符串可以写成 `"confirm"`、`"CONFIRMED"` 或任意错别字，编译器无法阻止；枚举只允许使用已经声明的值，错误能更早暴露。

枚举适合订单状态、支付状态、用户角色等“值的范围有限且固定”的概念，不适合名称、备注等自由文本。

## 2. 状态变化应由业务命令完成

对象的状态不应由外部随意赋值，而应通过有业务含义的方法改变：

```text
confirm(...) 表示“确认报价”这一业务动作
setStatus(...) 只是“把字段改成某个值”
```

业务方法可以集中保护规则，例如只有草稿、未过期且包含明细的报价才能确认。这样调用者不能绕开规则直接制造非法状态。

确认、取消、付款这类动作通常是用户或其他系统明确发出的命令。定时任务适合每天清理过期数据、周期性生成报表等后台工作，不应代替一个需要明确确认的业务动作。

## 3. 状态机的核心是“允许哪些变化”

状态建模不只是增加一个字段，还要定义：

- 当前状态允许执行哪些操作；
- 什么条件满足时才能进入下一状态；
- 操作成功后哪些数据发生变化；
- 操作失败后对象必须保持什么状态。

例如，已确认报价不再允许增删明细，是因为确认代表内容已经定稿。重要的不是 `if` 写在哪里，而是对象始终不能进入互相矛盾的状态。

## 4. 布尔方法的名字必须与返回值含义一致

布尔方法应读起来像一个能回答“是或否”的问题：

```text
isValidOn(date)      指定日期是否有效？
isExpiredOn(date)    指定日期是否过期？
```

如果方法叫“是否有效”，有效时就应返回 `true`；不要让名字表达“有效”，实现却返回“已过期”。清楚的命名能减少调用处的取反和误判。

## 5. 日期边界必须先写成业务规则

假设报价有效期为 8 月 25 日，常见规则是：

```text
8 月 24 日：有效
8 月 25 日：有效
8 月 26 日：无效
```

它表达的是：

```text
查询日期 <= 有效期
```

日期边界最容易出现“差一天”错误，因此至少测试有效期之前、有效期当天、有效期之后。先用自然语言确定边界是否包含，再选择日期比较方法。

## 6. 时间应当作为输入，而不是隐藏条件

直接在业务方法深处读取系统当前日期，会让结果随着运行日期改变；把某个真实日期硬编码到生产校验中，又会让规则只能在那个时间附近工作。

更容易测试和复用的设计是：

```text
业务方法显式接收“用于判断的日期”
测试传入固定日期
程序入口在真正执行时传入当前日期
```

这样测试在任何一天运行都得到相同结果。更复杂的项目可以注入 Java 的 `Clock`，本质仍然是把时间当成可替换的依赖。

## 7. 修改状态前完成全部校验

可靠的业务操作遵循：

```text
检查参数 → 检查当前状态 → 检查业务条件 → 最后修改状态
```

如果先把状态改成“已确认”，随后才发现报价为空或已经过期并抛出异常，对象就会留下半完成状态。

这种“失败后保持原样”的性质叫失败原子性。它同样适用于库存扣减、余额转账、数据库事务和批量更新。

## 8. 参数错误与状态错误要区分

- `IllegalArgumentException`：调用者传入的参数本身不合法，例如日期为 `null`、数量为负数。
- `IllegalStateException`：参数可能合法，但对象当前状态不允许这个动作，例如已确认报价再次增删明细。

区分异常能让调用者知道应该修改输入，还是停止当前操作并处理业务状态。

## 9. 一个测试只锁定一个主要规则

如果多个失败分支抛出同一种异常，一个宽泛测试很容易“因错误原因而通过”。例如本想验证“过期不能确认”，却因为报价为空先抛出了异常。

可信测试应让其他前置条件全部合法，只留下一个被测条件：

```text
测试过期：报价非空、状态为草稿，只让日期过期
测试空报价：日期有效、状态为草稿，只让明细为空
测试重复确认：先合法确认一次，再执行第二次确认
```

因此，不同业务分支应使用独立测试，并明确验证预期异常、返回值和关键状态。

## 10. 状态操作的测试矩阵

对一个会改变状态的方法，至少从四个方向检查：

| 场景 | 结果 | 状态要求 |
|---|---|---|
| 合法输入、合法状态 | 成功 | 精确变为目标状态 |
| 非法参数 | 失败 | 原状态不变 |
| 当前状态不允许 | 失败 | 原状态不变 |
| 业务条件不满足 | 失败 | 原状态不变 |

还应测试关键边界，例如日期当天是否包含、重复执行是否允许、确认后是否还能修改内容。

## 11. 可迁移审查清单

- 有限取值是否使用枚举，而不是自由字符串？
- 状态是否只能通过有业务含义的方法改变？
- 每个状态允许和禁止的操作是否明确？
- 布尔方法名与 `true` 的含义是否一致？
- 日期边界是否明确包含或不包含当天？
- 时间是否作为输入或依赖，避免隐藏的系统时间和生产魔法日期？
- 所有校验是否发生在状态修改之前？
- 参数错误与对象状态错误是否区分？
- 每个失败分支是否由独立测试准确命中？
- 失败后关键字段、集合和金额是否保持不变？
