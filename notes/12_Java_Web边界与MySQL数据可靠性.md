# Java Web 边界与 MySQL 数据可靠性

## 1. 本章解决什么问题

一个后端功能并不是“收到请求后把数据塞进数据库”这么简单。可靠链路至少包含：

```text
外部请求
→ HTTP 接口层
→ 应用服务层
→ 领域规则
→ 数据访问层
→ 数据库约束
```

每一层都要回答不同的问题：

- HTTP 层负责协议：路径、参数、状态码和 JSON；
- 应用服务负责组织一次完整用例；
- 领域层负责业务对象是否合法、状态能否变化；
- 数据访问层负责把对象转换成持久化操作；
- 数据库负责在并发和程序缺陷存在时仍守住最低数据底线。

可靠性来自多层边界共同工作，不来自某一个框架注解或某一条 SQL。

## 2. 先定义契约，再选择异常和状态码

异常类型不是为了让测试变绿，而是为了表达失败的性质。常见失败至少应区分：

| 失败类别 | 含义 | 常见 HTTP 结果 |
|---|---|---|
| 输入非法 | 请求值为空、格式错误、超出允许范围 | 400 Bad Request |
| 资源不存在 | 标识符合法，但目标记录确实不存在 | 404 Not Found |
| 资源冲突 | 唯一键重复、状态与当前操作冲突 | 409 Conflict |
| 状态不允许 | 对象存在，但当前生命周期不能执行该行为 | 409 或明确的业务错误 |
| 程序缺陷 | 未预期的空指针、依赖故障、代码错误 | 500 Internal Server Error |

`NullPointerException` 尤其需要谨慎。它既可能来自主动的非空检查，也可能来自真正的程序漏洞。若全局把所有空指针都转换成 400，就会把服务器错误伪装成用户错误，使监控、排障和客户端处理全部失真。

更可靠的原则是：

1. 在业务入口主动校验外部输入，抛出含义明确的异常；
2. 只转换已经确定语义的异常；
3. 未预期异常保留为 500，并在服务端记录完整原因；
4. 对外错误结构稳定，但不泄露堆栈、SQL、路径和凭据。

## 3. 异常翻译属于系统边界

领域对象不应知道 HTTP。一个商品编号、账户余额或订单状态在控制台程序、批处理和 Web 服务中都应服从同一业务规则，但只有 Web 层需要决定 400、404 或 409。

因此可以形成这样的依赖方向：

```text
领域异常或参数异常
        ↓
Web 异常处理器翻译
        ↓
HTTP 状态码 + 稳定错误 JSON
```

错误响应通常至少包括：

- 稳定的状态或业务错误码；
- 简短错误类别；
- 面向调用者的消息；
- 在复杂系统中可增加请求标识，方便关联日志。

不要让领域层返回 `ResponseEntity`，也不要让控制器重复编写相同的 `try/catch`。协议转换集中在边界层，业务规则留在领域层。

## 4. Controller、Service 与响应对象的职责

### Controller

控制器负责接收协议输入并返回协议输出。它应当薄：

- 声明路径和 HTTP 方法；
- 读取路径、查询或请求体参数；
- 调用应用服务；
- 返回响应对象。

控制器不适合承担复杂字符串解析、集合遍历、数据库拼接和大量业务判断。

### Service

应用服务描述一个用例，例如“解析编码”“创建草稿”“确认报价”。它可以协调多个领域对象和仓储，但不应变成所有逻辑的堆放处。

### Response DTO

响应对象是对外契约，不等同于领域对象或数据库行。使用独立响应对象有三个价值：

1. 防止内部字段被意外暴露；
2. 领域模型变化时减少对外接口震荡；
3. 明确 JSON 中哪些字段允许缺失、为 `null` 或必须存在。

Java `record` 适合表达只承载数据、创建后不再修改的响应值，但是否使用它取决于语义，而不是为了追求新语法。

## 5. Web 测试必须验证完整可观察结果

只断言 HTTP 400，只能证明请求失败，不能证明失败原因正确。请求也可能因为路由错误、序列化错误或程序崩溃而得到某个非成功状态。

一个典型接口测试应检查：

```text
请求输入
→ HTTP 状态
→ JSON 关键字段
→ 必要时检查状态是否改变
```

成功测试通常验证状态码和响应字段；失败测试通常验证状态码、稳定错误类别、消息中的关键含义，以及失败后数据没有被写入。

测试仍要保持单一原因原则：验证格式错误时，其他条件必须合法；验证不存在时，标识符本身必须合法。否则测试可能从错误分支通过。

## 6. 关系模型的基本组成

关系表可以理解为一组受结构和约束管理的记录：

- 表表达一类事实；
- 行表达一条具体事实；
- 列表达事实的一个属性；
- 数据类型限定属性的机器表示；
- 约束限定哪些状态允许进入数据库。

建表不是把 Java 字段机械翻译成 SQL 列。需要先判断：

- 这张表表达什么事实；
- 哪些字段构成身份；
- 哪些字段允许暂缺；
- 哪些值由其他值推导；
- 哪些规则必须在并发下仍成立。

## 7. 主键与业务唯一键不是一回事

数据库内部主键用于稳定识别一行，业务唯一键用于表达现实世界中的唯一身份。

例如可以同时存在：

```text
id            数据库内部身份，稳定且不表达业务含义
business_code 业务身份，需要唯一，但未来可能纠错或改变
```

常见设计是使用数值主键，并为业务编码增加 `UNIQUE`。这样其他表可以引用稳定主键，业务编码修改时不必级联修改所有引用。

但这不是绝对规则。选择自然主键还是代理主键，需要考虑业务键是否短小、稳定、永不复用，以及是否会成为大量外键。关键是明确两种身份各自承担什么责任。

## 8. 数据类型本身就是契约

### 文本

`VARCHAR(n)` 表示变长文本。长度不是随便填写的装饰，应来自格式上限、索引成本和业务规则。机器标识符还应明确是否区分大小写、是否允许首尾空白以及采用何种字符集。

### 整数

`INT` 适合明确范围内的整数；`BIGINT` 提供更大范围。自增主键使用哪一种，应根据预期数据量和生命周期选择，而不是所有表统一照抄。

### 金额

十进制金额通常使用 `DECIMAL(precision, scale)`：

- `precision` 是总有效数字位数；
- `scale` 是小数位数。

它对应精确十进制语义，适合与 Java `BigDecimal` 配合。`FLOAT`、`DOUBLE` 使用二进制浮点近似，不适合要求精确相等和结算的金额。

### ENUM

数据库枚举能限制有限值，适合取值非常稳定的小型系统。但它也会带来数据库方言绑定和修改值需要变更表结构的问题。跨数据库系统或频繁演进的业务，常用 `VARCHAR + CHECK`、代码表或外键表达有限取值。

选择 `ENUM` 前要回答：值是否稳定、是否需要国际化、是否会被外部系统共享、改变取值是否能接受数据库迁移。

## 9. `NULL`、空字符串和零是三种不同状态

```text
NULL ＝ 未知、缺失或暂未提供
''   ＝ 已提供一个长度为零的字符串
0    ＝ 已提供数值零
```

三者不能互相替代。例如草稿中的尺寸为 `NULL` 可以表示尚未解析；尺寸为 `0` 可能违反业务规则；空后缀究竟使用 `NULL` 还是空字符串必须由契约统一决定。

SQL 使用三值逻辑：比较结果除了真、假，还有未知。表达式：

```sql
nullable_number > 0
```

当字段为 `NULL` 时结果是未知，而不是假。MySQL 的 `CHECK` 主要拒绝结果为假的行，未知值可能通过。因此：

- 要求必须填写：`NOT NULL` 与值域 `CHECK` 通常要同时存在；
- 允许草稿缺失：可以保留可空，同时用 `CHECK` 拒绝已填写的非法值。

查询 `NULL` 必须使用 `IS NULL` 或 `IS NOT NULL`，不能使用 `= NULL`。

## 10. 草稿状态与正式状态的建模

草稿允许不完整，正式状态要求完整，这是许多业务系统的共同问题。常见方案有两类。

### 单表加状态

同一张表保存草稿和正式记录，通过状态列区分。优点是身份连续、无需搬运数据；缺点是数据库列往往必须允许 `NULL`，复杂的“状态相关约束”需要应用层或更复杂的数据库约束保证。

### 草稿表与正式表分离

草稿和正式数据进入不同表。优点是正式表可以保持严格完整性；缺点是提交时需要复制或迁移数据，并通过事务保证删除草稿、写入正式表和关联数据要么一起成功，要么一起失败。

不能仅凭“草稿允许空”就自动决定必须分表。应比较：

- 两种状态的字段结构是否明显不同；
- 草稿是否需要长期保留和审计；
- 提交是否会生成新的业务身份；
- 跨表迁移带来的事务和查询复杂度是否值得。

## 11. 原始值、派生值与一致性

如果一个字段可以从另一个字段解析或计算得到，就必须确定真正的数据源。

例如：

```text
结构化编码 → 解析得到类别、尺寸和后缀
```

同时保存原始编码和解析字段属于有意冗余。它可以提高查询效率和可读性，但会产生一致性风险：编码修改后，派生字段可能仍保留旧值。

可靠写入流程是：

```text
接收原始值
→ 标准化并解析
→ 校验显式字段与解析结果是否一致
→ 一次性写入
```

若草稿允许派生字段缺失，可以规定：未填写时由系统补全；已经填写时必须与解析结果一致。正式提交前必须完成最后一次整体校验。

复杂编码解析通常更适合放在 Java 领域层，而不是复制成难以维护的 SQL 字符串逻辑。数据库仍负责通用约束，例如唯一性、非空、引用完整性和简单值域。

## 12. 为什么 Java 校验和数据库约束都需要

前端校验改善交互，Java 校验表达业务，数据库约束保护最终数据。三层不是重复浪费：

```text
前端：尽早提示
Java：集中业务语义和清晰错误
数据库：守住所有写入通道的最终底线
```

仅在 Java 中“先查询是否重复，再插入”还存在并发竞态：两个请求可能同时查询到不存在，然后同时插入。数据库唯一约束才能在最终写入点可靠仲裁。

应用需要捕获数据库冲突并翻译成稳定业务错误，但不能因为已有数据库约束就取消 Java 的友好校验。一个负责体验和语义，一个负责最终一致性。

## 13. CRUD 是状态变化，不只是四个关键字

- `INSERT` 创建新事实；
- `SELECT` 读取当前事实；
- `UPDATE` 修改已有事实；
- `DELETE` 删除事实。

每次写操作都要问：

- `WHERE` 是否准确限定目标；
- 预期影响几行；
- 零行受影响表示不存在、条件未变化还是错误；
- 多行受影响是否符合业务预期；
- 失败后已有状态是否保持不变。

尤其是 `UPDATE` 和 `DELETE`，缺少 `WHERE` 会影响整张表。正式执行前可以先用同一条件 `SELECT` 检查目标，并在事务中验证影响行数。

## 14. 事务与失败原子性

事务用于把多个数据库操作组成一个不可分割的业务单元。ACID 常被概括为：

- 原子性：全部成功或全部失败；
- 一致性：事务前后数据库满足约束；
- 隔离性：并发事务之间具有规定的可见性；
- 持久性：提交成功后结果不会因普通故障消失。

测试写操作时可以使用：

```text
开始事务
→ 插入测试数据
→ 查询、修改、删除并断言
→ 回滚
→ 再次确认数据不存在
```

但要注意 MySQL 中许多 DDL 操作会隐式提交，例如建表。不能假设把 `CREATE TABLE` 放进事务后，后续插入失败就会自动撤销表结构。数据库结构迁移和业务数据事务是两个不同层次的问题。

## 15. 数据库迁移脚本的职责

迁移脚本是数据库结构的版本历史。它的核心目标是让不同环境从同一旧版本可靠升级到同一新版本。

可靠迁移应具有：

- 唯一且有顺序的版本；
- 已执行版本不再随意修改；
- 结构变化和普通演示数据分离；
- 不包含密码、个人路径和本机专属配置；
- 在干净数据库上能够执行；
- 在升级前明确失败和回滚策略。

使用 Flyway 等工具时，常见版本脚本名称形如：

```text
V1__create_catalog_table.sql
V2__add_unique_constraint.sql
```

双下划线用于分隔版本和描述。数据库连接配置决定目标数据库，因此迁移脚本通常不负责创建服务器级数据库，也不写固定的 `USE`。但在纯手工学习阶段，一个包含建库和选库语句的独立初始化脚本也可以存在；必须明确它不是最终的自动迁移形态。

初始化结构、生产基础字典数据、演示数据和测试数据是不同资产，不应全部混进同一个版本脚本。

## 16. 数据库测试矩阵

### 正常路径

- 创建结构成功；
- 插入完整记录成功；
- 插入允许缺失的草稿记录成功；
- 按唯一键查询成功；
- 更新只影响目标行；
- 删除只影响目标行。

### 约束路径

- 重复唯一键被拒绝；
- 必填列为 `NULL` 被拒绝；
- 空白机器标识符被拒绝；
- 大小写不符合规范时被拒绝或统一标准化；
- 已填写的数值越界被拒绝；
- 枚举或外键取值不存在时被拒绝。

### 失败后的状态

- 失败写入没有留下半行数据；
- 原有记录没有被覆盖；
- 事务回滚后测试数据消失；
- 结构迁移失败时能够判断哪些 DDL 已经生效。

测试不能只看到错误就结束，还要检查失败后的数据库状态。

## 17. 凭据与最小权限

数据库密码不能进入源码、SQL、提交历史或聊天记录。应用运行时也不应长期使用 `root`。

更合理的生产方向是：

- 为应用创建独立数据库账户；
- 只授予运行所需的最小权限；
- 开发、测试和生产使用不同凭据；
- 通过环境变量、密钥服务或受保护配置注入；
- 日志和异常信息不得打印密码与完整连接串。

本机为了临时验收保存的加密登录配置，也应在任务结束后删除。加密保存降低了明文暴露风险，但不等于可以永久无限制保留高权限账户。

## 18. 从数据库到 Java 持久化的后续顺序

在引入 ORM 前，应先理解最小数据库链路：

```text
Java 对象
→ SQL 参数
→ 数据库行
→ 查询结果
→ Java 对象
```

需要掌握连接生命周期、参数化 SQL、结果映射、事务边界和异常翻译。直接进入大型 ORM 而不了解这些基础，容易只会调用 `save()`，却无法解释生成的 SQL、事务何时提交、唯一冲突在哪里发生，以及慢查询如何定位。

学习顺序可以是：

1. 手写 SQL 与约束；
2. 理解 JDBC 的连接、预编译语句和结果集；
3. 使用 Spring 的轻量数据库访问工具减少样板代码；
4. 在确有需要时再引入 MyBatis 或 JPA；
5. 始终能够查看和解释最终 SQL。

## 19. 掌握证据的分级

- 文件存在：只能证明成果出现过；
- 脚本在干净环境执行：证明当前结构可复现；
- 正反测试通过：证明已检查的约束成立；
- 能解释失败原因：证明不只是碰巧运行；
- 间隔后独立迁移：证明知识能够复用。

AI 代为执行数据库测试可以提供工程验证，但不能单独证明学习者已经掌握 SQL。达到独立掌握，需要在不复制原脚本的情况下，根据新业务约束重新设计一张表，并能预测正常与失败结果。

## 20. 自测与迁移练习

### 口头问题

1. 为什么 400、404 和 500 不能只根据异常类名随意决定？
2. 为什么不应全局把所有 `NullPointerException` 转换成 400？
3. Controller、Service、领域对象和数据库各守哪一层边界？
4. 主键与业务唯一键有什么区别？
5. `NULL`、空字符串和数值零分别表示什么？
6. 为什么 `CHECK (value > 0)` 不一定拒绝 `NULL`？
7. 为什么 Java 已检查重复，数据库仍需要 `UNIQUE`？
8. 为什么建表成功后，后续插入失败不一定会让表自动消失？
9. 单表状态方案和草稿、正式分表方案各有什么代价？
10. 为什么数据库密码不能放进 Git，即使仓库暂时是私有的？

### 独立迁移题

不参考现有实现，设计一个供应商申请模块：申请阶段允许联系人和结算周期暂缺，正式启用前必须完整；供应商编码忽略首尾空白并要求唯一；信用额度不能为负。说明你选择单表状态还是草稿、正式分表，并为重复编码、空编码、负额度、合法草稿和正式提交各设计一个测试。

随后说明：哪些规则由前端提前提示，哪些由 Java 领域层表达，哪些必须由数据库约束兜底，以及一次正式提交应包含在哪个事务边界中。
