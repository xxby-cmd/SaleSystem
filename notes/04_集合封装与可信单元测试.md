# 集合封装与可信单元测试

## 1. 先根据业务语义选择集合

- `List`：元素有顺序，允许按位置访问，默认允许重复。
- `Set`：只关心成员是否存在，并要求元素不重复。
- `Map<K, V>`：按唯一键查找值，适合“产品编码 → 产品”这类映射。

变量通常声明为接口类型，创建时再选择具体实现：

```java
private final List<Item> items = new ArrayList<>();
```

这样业务代码依赖的是“列表能力”，而不是 `ArrayList` 的具体实现。泛型 `List<Item>` 把元素类型约束放到编译期，读取时不需要强制转换，也能尽早阻止错误类型进入集合。

## 2. 集合应有明确所有者

业务单据中的明细应属于某个具体单据，因此通常使用实例字段：

```text
quotationA.items 与 quotationB.items 相互独立
```

如果把可变集合声明为 `static`，它会成为整个 JVM 共享的全局状态，容易造成对象之间串数据、测试顺序依赖和并发问题。

判断原则：

> 状态属于某个对象，就放在对象实例中；只有确实需要全局共享且生命周期明确的状态，才考虑静态字段。

## 3. 聚合对象负责保护整体不变量

明细对象只保证自身字段合法，单据对象还要保护跨明细规则，例如：

- 不接受 `null` 或不完整明细；
- 同一产品不能重复加入；
- 总额等于全部明细小计之和；
- 添加或删除失败后，原状态保持不变。

可靠的修改顺序是：

```text
校验输入 → 检查业务冲突 → 修改集合
```

不要先加入集合再校验。否则异常虽然抛出了，内部状态却可能已经被污染。这个原则可以迁移到数据库事务、批量更新和库存扣减：失败应尽量做到“全部不生效”，而不是留下半成品状态。

## 4. `BigDecimal` 累加必须接收返回值

`BigDecimal` 是不可变对象，`add()` 不会修改原对象：

```java
BigDecimal total = BigDecimal.ZERO;
for (Item item : items) {
    total = total.add(item.getSubtotal());
}
```

如果只调用 `total.add(...)` 而不接收返回值，`total` 仍然是原来的零。聚合金额时应从明确的单位元 `BigDecimal.ZERO` 开始，并逐项生成新的累计值。

## 5. 返回集合时保护内部结构

直接返回内部可变列表，会让调用者绕过 `addItem()`、重复校验和其他业务规则：

```java
return List.copyOf(items);
```

`List.copyOf()` 返回不可修改的列表视图快照，能够阻止外部增删集合结构。但它是浅层保护：列表中的元素仍是原对象引用，如果元素本身可变，调用者仍可能修改元素字段。

因此要区分：

- 集合结构不可变；
- 集合元素不可变；
- 聚合整体不变量不可被绕过。

第一项可由防御性复制解决；后两项通常需要不可变元素、受控修改方法或复制对象。

## 6. 遍历期间删除要使用安全入口

增强 `for` 适合只读遍历，不应在遍历过程中直接调用列表的 `remove()`，否则可能触发并发修改异常。按条件删除可以使用：

```java
items.removeIf(item -> matches(item));
```

需要更复杂的遍历和删除控制时使用 `Iterator`。选择方式取决于是否只读、是否删除以及是否需要索引，不要为使用某种语法而使用。

## 7. 测试必须能够排除错误实现

### 7.1 期望值必须独立

如果生产代码通过 `getSubtotal()` 计算总额，测试又用同一个 `getSubtotal()` 生成期望总额，那么两处一起算错时测试仍可能通过。

```text
生产逻辑算实际值；测试用人工推导的固定结果验证实际值。
```

测试不是重复执行实现，而是用独立依据判断实现是否正确。

### 7.2 异常必须来自目标边界

要测试 `quotation.addItem(item)` 拒绝不完整明细，就必须先成功创建一个不完整对象，再单独调用 `addItem()`。如果异常在构造器中已经抛出，只能证明构造器拒绝了输入，不能证明 `addItem()` 的校验有效。

### 7.3 不要根据实际结果选择断言

下面这种思路没有验证能力：

```text
如果返回成功，就断言成功状态；否则断言失败状态。
```

它接受了互相矛盾的两种结果。测试必须在执行前确定契约：删除存在元素应返回 `true`，删除不存在元素应返回 `false`，并分别验证集合和总额状态。

### 7.4 同时验证返回值和状态

一次业务操作可能同时包含：

- 返回值或异常；
- 集合数量变化；
- 汇总金额变化；
- 失败后状态是否保持不变。

只检查其中一项可能漏掉“返回值正确但状态错误”或“状态正确但返回值错误”。关键写操作应验证结果和关键副作用。

## 8. 测试隔离取决于状态生命周期

JUnit 5 默认会为每个测试方法创建新的测试类实例。因此测试类的普通实例字段通常不会跨测试共享，不需要为了形式统一而清空。

真正需要重置的是跨测试存活的状态，例如：

- 生产代码中的 `static` 可变集合；
- 测试类中的静态字段；
- 外部数据库、文件或缓存；
- 被多个测试复用的共享依赖。

`@BeforeEach` 的目的，是为每个测试建立明确且一致的前置条件，而不是无条件调用 `clear()`。

## 9. 可迁移审查清单

- 集合类型是否符合顺序、唯一性和查找方式？
- 是否通过泛型在编译期约束元素类型？
- 可变状态是否属于正确的对象，而不是意外全局共享？
- 所有校验是否发生在状态修改之前？
- 聚合计算是否正确处理不可变值对象？
- 外部是否能绕过业务方法直接修改内部集合？
- 测试期望是否独立于生产实现？
- 异常是否确实来自想验证的方法和规则？
- 测试是否预先确定唯一正确结果？
- 写操作是否同时验证返回值、状态变化和失败不变性？
